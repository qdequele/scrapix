# Monitoring

Scrapix exposes Prometheus metrics from every service and ships with a pre-configured monitoring stack (Prometheus + Grafana + AlertManager).

## Quick Start

The monitoring stack lives in `deploy/monitoring/`:

```bash
cd deploy/monitoring
docker compose up -d
```

| Service | URL | Credentials |
|---------|-----|-------------|
| Prometheus | http://localhost:9091 | — |
| Grafana | http://localhost:3000 | admin / scrapix |
| AlertManager | http://localhost:9093 | — |

## Metrics Endpoint

The engine (`scrapix-api`) exposes unauthenticated Prometheus text-format
metrics at `GET /metrics` on its normal HTTP port (`PORT`, default `8080`):

```bash
curl http://localhost:8080/metrics
```

Every worker (`scrapix-worker-crawler`, `scrapix-worker-content`,
`scrapix-frontier-service`) exposes the same `GET /metrics` (and `GET
/health`) on its `WAKE_PORT` (default `8081`) — the same bare-TCP listener
Fly's proxy connects to for autostart:

```bash
curl http://localhost:8081/metrics
```

There is no `METRICS_PORT` variable; each service's metrics live on its own
HTTP/wake port as above.

## Key Metrics

All metrics are defined once in `crates/scrapix-core/src/metrics.rs` and
registered against a single process-wide registry (so `scrapix all` exposes
every metric from one `/metrics` call). Metric names are a contract with
`qdq-server/monitoring` — don't rename without updating the scrape config
there.

| Metric | Type | Labels | Emitted by | Description |
|--------|------|--------|------------|-------------|
| `scrapix_crawler_fetches_total` | Counter | `outcome` (`crawled`/`not_modified`/`retry`/`failed`) | crawler worker | Total URL fetches handled |
| `scrapix_crawler_fetch_duration_seconds` | Histogram | — | crawler worker | Wall time of one fetch attempt |
| `scrapix_crawler_bytes_total` | Counter | — | crawler worker | Bytes downloaded by successful fetches |
| `scrapix_frontier_admissions_total` | Counter | `result` (`admitted`/`duplicate`/`error`) | frontier | Total URL admission attempts |
| `scrapix_frontier_queued` | Gauge | `job` | frontier | Queued URL count, top 50 jobs by queue size only |
| `scrapix_frontier_dispatched_total` | Counter | — | frontier | URLs dispatched to the crawl topic |
| `scrapix_content_documents_total` | Counter | `outcome` (`success`/`failure`/`skipped`/`duplicate`) | content worker | Pages handled |
| `scrapix_content_flush_duration_seconds` | Histogram | — | content worker | Time to flush one storage backend |
| `scrapix_api_jobs` | Gauge | `status` | engine | In-memory job count by status |
| `scrapix_consumer_uncommitted` | Gauge | `topic` | every Kafka consumer | In-flight (unacked) message count per topic, sampled once per commit tick |

<Note>
  Metric names and labels below this table (fetch/processing/robots/DNS/AI/storage/browser
  metrics with a `scrapix_*` prefix not in the table above) do not exist in
  the running services — they were an earlier design's aspirational list.
  Only the metrics in the table above are actually registered and served.
</Note>

## Prometheus Scrape Configuration

Point Prometheus at the engine's HTTP port and each worker's `WAKE_PORT`:

```yaml
scrape_configs:
  - job_name: scrapix-api
    static_configs:
      - targets: ["host.docker.internal:8080"]

  - job_name: scrapix-crawler-workers
    static_configs:
      - targets:
          - "host.docker.internal:8081" # WAKE_PORT, one per crawler machine

  - job_name: scrapix-content-workers
    static_configs:
      - targets:
          - "host.docker.internal:8081" # WAKE_PORT, one per content-worker machine

  - job_name: scrapix-frontier
    static_configs:
      - targets: ["host.docker.internal:8081"] # WAKE_PORT

  - job_name: redpanda
    static_configs:
      - targets: ["host.docker.internal:9644"]
    metrics_path: /public_metrics

  - job_name: meilisearch
    static_configs:
      - targets: ["host.docker.internal:7700"]
    metrics_path: /metrics
```

In a multi-machine deployment (Fly, Kubernetes), each worker machine listens
on the same `WAKE_PORT` (8081 by default), so scrape targets need one entry
per machine/pod, not per logical service.

## Alert Rules

Pre-configured alerts in `deploy/monitoring/prometheus/alerts.yml`:

### Crawler Alerts

| Alert | Condition | Severity |
|-------|-----------|----------|
| High Error Rate | Error rate > 10% for 5 minutes | warning |
| Crawler Worker Down | No metrics for 2 minutes | critical |
| Low Throughput | < 1 page/min for 10 minutes (when queue > 0) | warning |
| High Fetch Latency | p95 > 10s for 5 minutes | warning |
| Queue Backlog | Queue > 100K for 15 minutes | warning |

### Content Alerts

| Alert | Condition | Severity |
|-------|-----------|----------|
| Content Worker Down | No metrics for 2 minutes | critical |
| High AI Token Usage | > 100K tokens/hour | warning |
| Extraction Failures | Failure rate > 20% for 5 minutes | warning |

### Infrastructure Alerts

| Alert | Condition | Severity |
|-------|-----------|----------|
| Kafka Consumer Lag | Lag > 10K for 10 minutes | warning |
| Meilisearch Down | Health check failing | critical |
| Redis Down | Ping failing | critical |
| High Memory Usage | > 90% for 5 minutes | warning |

### Job Alerts

| Alert | Condition | Severity |
|-------|-----------|----------|
| Stuck Job | No progress for 30 minutes | warning |
| Long Running Job | Running > 24 hours | warning |

## AlertManager Configuration

Routes are pre-configured with placeholder receivers:

```yaml
route:
  group_by: ['alertname', 'job']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - match:
        severity: critical
      group_wait: 10s
      receiver: critical-receiver
    - match:
        severity: warning
      receiver: warning-receiver
```

Configure receivers for your notification channels (Slack, PagerDuty, email) in `deploy/monitoring/alertmanager/alertmanager.yml`.

## Grafana

Grafana is pre-provisioned with Prometheus as a datasource. Import or build dashboards for:

- **Crawl throughput** — pages/sec, bytes/sec over time
- **Error rate** — by domain, status code
- **Queue depth** — frontier queue size over time
- **Latency percentiles** — p50, p95, p99 fetch times
- **Worker utilization** — active fetches vs capacity
