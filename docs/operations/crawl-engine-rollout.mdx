# Crawl Engine Rollout

This is the deploy checklist for rolling the `crawl-engine-fixes` branch out
to the production box (`hackersearch`, deployed from the separate
`qdq-server` repo, systemd-managed, env in `/etc/scrapix/scrapix.env`). It is
a checklist, not automation — work through it in order.

<Note>
The Rails app (the Lab) and the console moved to their own repo,
[`meilisearch/lab`](https://github.com/meilisearch/lab). Every Rails command
below (`bin/rails …`, the Lab's migrations and tests, the analytics parity
script) runs from a `meilisearch/lab` checkout, not from this repo.
</Note>

## Pre-deploy checklist

- [ ] **Set `SCRAPIX_MODE=hosted`** on every hosted API (qdq-server env file, Fly, Heroku, k8s) and restart, **before** deploying an engine that includes standalone mode. The old binary ignores the variable; the new one refuses to start without it (it would otherwise start in standalone mode and ask for `SCRAPIX_ADMIN_KEY`).
- [ ] **Local dev: refresh an existing `.env`.** `just dev` in this repo now runs the engine **standalone** (`.env.example` sets `SCRAPIX_MODE=standalone` and a dev `SCRAPIX_ADMIN_KEY`); an `.env` copied from the old hosted dev setup still points `DATABASE_URL` at the Rails database and sets `SCRAPIX_MODE=hosted`. Re-copy `.env.example`, or use its commented "Hosted against a local Lab" block with the Lab running from a `meilisearch/lab` checkout.
- [ ] **Set `LAB_URL`, `LAB_INSTANCE_ID`, `LAB_INSTANCE_SECRET` and `LAB_SERVICE_TOKEN`** on every hosted API (the instance id and secret are minted by the Lab with `bin/rails lab:hosted_engine:create`; `LAB_SERVICE_TOKEN` is the same value on the Lab) — the hosted engine refuses to start without them, and refuses a Lab that predates contract v2 (no `GET /internal/instances/me`), so deploy the Lab first. `LAB_EVENTS_SECRET` is ignored now (warned at boot): remove it. Dashboards filtering `scrapix_lab_requests_total` on `endpoint="ping"` must switch to `endpoint="instances_me"`, and `scrapix_lab_events_delivered_total` gains `outcome="dropped"` (events never acknowledged for 24 h). If production still runs an engine from before the Lab split, do **not** do the two rollouts below one after the other: follow "Lab split phase 1" as a single ordered rollout (it carries the boundary steps it needs). (`JWT_SECRET` is Rails-only now: the engine ignores it. `LAB_EVENTS_URL` is the deprecated pre-split spelling of `LAB_URL`.)
- [ ] **`GET /ws/job/{id}` now requires auth.** The console's live job updates need the `scrapix_session` cookie to be readable on a parent domain shared with the API — set `SESSION_COOKIE_DOMAIN` (e.g. `scrapix.meilisearch.com`, which covers `api.scrapix.meilisearch.com`) before deploying, or the console's WebSocket connection will be rejected.

## Engine ↔ Lab boundary rollout

<Warning>
If production has not done this rollout yet, **do A and B, then skip C and D
and follow "Lab split phase 1" below as one ordered rollout.** It stops the old
engine before Rails is deployed, which C and D on their own would not, and it
carries the parts of C, D and E it needs (the Rails secrets, the cron switch,
the checks). B (the duplicate-payment-intent check) must run before the Rails
migrations. Sections C and D are kept for the record, and for readers whose
production already ran them.
</Warning>

The engine no longer writes the Rails-owned tables. It reports usage and job
lifecycle as signed **lab events** (see [Lab Events](/api-reference/lab-events)),
and the Rails app (the "Lab") debits the ledger, runs auto top-up, sends job
and low-balance emails, fires saved-config cron and sweeps expired OAuth
rows. Its original order was **Rails first, engine second, cron last**, so no
window exists where a charge is lost or a crawl fires twice. (The Lab split
changes the Rails-versus-engine order: see the warning above and "Lab split
phase 1".)

### A. Credentials

```bash
# on the Lab (meilisearch/lab checkout), once per engine deployment:
bin/rails lab:hosted_engine:create PRODUCT=scrapix REGION=<region> URL=<the engine's public URL>
# prints instance_id, secret (64 hex, shown once) and lab_url

openssl rand -hex 32   # LAB_SERVICE_TOKEN
```

`LAB_INSTANCE_ID` and `LAB_INSTANCE_SECRET` come from the Lab, not from
`openssl`: set the printed `instance_id` and `secret` on the engine
(`scrapix-api`). The engine presents them on every `{LAB_URL}/internal/*` call
(`X-Lab-Instance-Id` + `Authorization: Bearer <LAB_INSTANCE_SECRET>`) and signs
its event batches with the secret. `LAB_SERVICE_TOKEN` is needed with an
**identical value** on the Lab and on the engine: it authenticates Lab →
engine calls only (the saved-config cron).
The engine also needs `LAB_URL`, the Lab's base URL (e.g.
`https://lab.meilisearch.com`, or `http://127.0.0.1:8091` when both run on
the box); events go to `{LAB_URL}/internal/events`. The hosted engine
**refuses to start** without `LAB_URL`, `LAB_INSTANCE_ID`,
`LAB_INSTANCE_SECRET` and `LAB_SERVICE_TOKEN`; a standalone engine refuses
`LAB_INSTANCE_ID`/`LAB_INSTANCE_SECRET`. (Before the Lab split `LAB_URL` was
`LAB_EVENTS_URL`, the full `…/internal/events` URL; it still works as a
deprecated fallback. Before contract v2 the engine signed with
`LAB_EVENTS_SECRET`, which is now ignored.)

### B. Before the Rails migrations: check for duplicate payment intents

The migration `20260929000003_add_lab_event_id_index_to_transactions` adds a
**unique index** on `transactions.metadata->>'stripe_payment_intent_id'` (one
credit grant per Stripe payment) unless it already exists. It fails if
production already holds duplicates — for example a payment credited twice.
Check first, in production:

```sql
SELECT metadata->>'stripe_payment_intent_id' AS payment_intent,
       count(*)                              AS grants,
       array_agg(id ORDER BY created_at)     AS transaction_ids,
       array_agg(account_id)                 AS account_ids
FROM transactions
WHERE metadata ? 'stripe_payment_intent_id'
GROUP BY 1
HAVING count(*) > 1;
```

The query must return **no rows**. If it returns any, the account was
credited more than once for one payment: resolve each case (usually deleting
or adjusting the duplicate `transactions` row and correcting the balance)
before migrating. An index of that name that already exists is left alone.

### C. Deploy Rails first, with `LAB_CRON_ENABLED` off

1. Set `LAB_EVENTS_SECRET` and `LAB_SERVICE_TOKEN` on the Rails app. Leave
   `LAB_CRON_ENABLED` **unset** (off): the old engine still runs its own
   cron scheduler, and enabling both would fire every scheduled crawl twice.
   Production must **not** inherit `.env.example`'s `LAB_CRON_ENABLED=true`
   (a dev convenience): if the production env was seeded from it, remove
   the line before this deploy and set it only at step E.
2. Check that Rails' `SCRAPIX_ENGINE_URL` points at the engine's API. Cron
   now runs in Rails and sends `LAB_SERVICE_TOKEN` there, so a wrong URL both
   breaks scheduled crawls and hands the token to whatever listens on it.
   The Rails default is `http://localhost:8080`; on qdq-server that port
   belongs to LUMEN and the engine is at `http://127.0.0.1:8090`. (Rails logs
   a warning at boot when `LAB_CRON_ENABLED=true` and `LAB_SERVICE_TOKEN` or
   `SCRAPIX_ENGINE_URL` is unset.)
3. Run the Lab's migrations (in `meilisearch/lab`: `cd saas && bin/rails db:migrate`) and deploy. **Not
   while an engine from before the Lab split is running:** `db:migrate` now
   includes `20260930000001_encrypt_meilisearch_engine_api_keys`, which
   encrypts `meilisearch_engines.api_key`, the column such an engine reads
   directly, so it would send the ciphertext to Meilisearch as the key. Stop
   that engine first (this is why "Lab split phase 1" is one ordered rollout).
   The migrations create `lab_events` (the engine's outbox),
   `lab_events_received`, `accounts.last_auto_topup_attempt_at` and
   `crawl_configs.last_error`. (From phase 1 on, the engine keeps `lab_events`
   in its own database and migrates it itself, so nothing on the engine side
   depends on this.)
4. Check that SolidQueue is running the recurring jobs
   (`process_lab_events` every 10 s, `run_due_crawl_configs` every 30 s,
   `cleanup_oauth_tokens` hourly). `run_due_crawl_configs` exits immediately
   while `LAB_CRON_ENABLED` is off.
5. Verify the endpoint answers: an unsigned request gets `401`, not `503`
   (`503` means `LAB_EVENTS_SECRET` is not set on Rails).

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -X POST \
     -H 'Content-Type: application/json' -d '{"events":[]}' \
     https://<rails-host>/internal/events   # expect 401
   ```

### D. Deploy the engine

The engine build that contains this rollout also needs its own database
(`scrapix_engine`) and `LAB_URL`, and refuses a Rails database: set those up
with steps 3 to 6 of "Lab split phase 1", not by pointing it at the Rails
`DATABASE_URL`.

Follow the normal service order in "4. Deploy order" below (content workers,
crawlers, frontier, then API), with `LAB_URL`, `LAB_EVENTS_SECRET` and
`LAB_SERVICE_TOKEN` set on the API, and with no jobs running (step 0). Also
update every hosted deploy config you use (Fly secrets, Heroku config vars,
the Kubernetes `scrapix-secrets` / `scrapix-config`) — they are listed in
`deploy/`.

After the API starts:

- [ ] `GET /metrics` shows `scrapix_lab_events_pending` (near 0) and
      `scrapix_lab_events_delivered_total{outcome="accepted"}` growing.
- [ ] Run a `/scrape` with a test account: a `usage_deduction` row
      (`scrape: <url> (N credits)`) appears in `GET /account/billing/transactions`
      within a few seconds, exactly once.
- [ ] `scrapix_lab_events_delivered_total{outcome="failed"|"rejected"}` stays
      flat. A growing `scrapix_lab_events_pending`, or an engine warning
      `Lab events backlog older than 10 minutes`, means Rails is unreachable
      or rejecting events (check the secret matches, then Rails logs for
      `Skipping malformed lab event`). Nothing is lost meanwhile: the outbox
      retries with backoff (max 5 min) forever.

### E. Enable cron

Only once the engine is upgraded (it no longer runs a cron scheduler), set
`LAB_CRON_ENABLED=true` on Rails and restart. Re-check first that Rails'
`SCRAPIX_ENGINE_URL` points at the upgraded engine (`http://127.0.0.1:8090`
on qdq-server, not the `http://localhost:8080` default) and that
`LAB_SERVICE_TOKEN` matches the engine's; a boot warning in the Rails log
means one of them is missing. Confirm a saved config with a
cron schedule fires (`last_run_at` / `last_job_id` set on the config; a
failure shows in `last_error`). Between D and E, scheduled crawls do not
fire — keep that window short.

### F. Rollback and caveats

- Rolling the **engine** back to the previous version is safe: it resumes its
  own direct ledger writes, but any events still pending in `lab_events` are
  no longer delivered — drain the outbox (`scrapix_lab_events_pending` at 0)
  before rolling back or those charges are never applied. After stopping the
  new engine (and before starting the old one), confirm nothing was left
  behind:

  ```sql
  SELECT count(*) FROM lab_events WHERE delivered_at IS NULL;  -- must be 0
  ```

  If it isn't 0, restart the new engine until it delivers them. Turn
  `LAB_CRON_ENABLED` off first, or scheduled crawls fire twice. (For rolling
  back the Lab split itself, use "Phase 1 rollback" below.)
- **Crash after a cancel.** Cancelling a job persists its terminal state a
  few seconds after the request (once the charge and the job event are
  recorded). If the API crashes within that window, the job is recovered as
  *running* and later ends `FailStalled` (billed for the pages crawled) and
  sends a "failed" email. The charge is **not** duplicated — the crawl's
  usage event has a deterministic id.
- Live job updates (`GET /ws/job/{id}`) still need `SESSION_COOKIE_DOMAIN`
  (see the pre-deploy checklist above) so the console can present the session
  cookie to the API.

## Lab split phase 1

The engine stops touching the Lab's database. It gets its own database
(`scrapix_engine`, migrated by the engine itself in both modes), asks the Lab's
`/internal/*` API for credentials, credits and Meilisearch targets through
`LAB_URL`, and serves the analytics pipes itself. Spec:
`docs/superpowers/specs/2026-09-30-lab-split-design.md` §8. Reference:
[Lab Events](/api-reference/lab-events#lab-internal-api).

**The order is deliberate: drain and stop the old engine first, then deploy
Rails.** The Rails release encrypts `meilisearch_engines.api_key` in place, and
the old engine reads that column directly, so an old engine left running would
send the ciphertext to Meilisearch as the key. Expect the public API to be down
from step 1 to step 6; pick a quiet window. (Numbered steps here are this
section's; "0. Drain…" and "4. Deploy order" further down are the general
sections of this page.)

1. **Take the public API out of Caddy, then drain and stop the old engine.**
   Remove the public API route (`api.scrapix.meilisearch.com` → 8090) from
   Caddy, or make it answer 503, and reload Caddy: the new engine is started
   once in step 4 only to migrate its database, and must not serve a request
   then (a job or a charge written before the data move makes the move script
   refuse to run, see step 5). Then follow "0. Drain or cancel running jobs
   first" below and stop `scrapix-api`. The frontier and workers can stay up,
   but no crawl may be running.
2. **Generate and set the encryption secrets, then deploy Rails.**
   - Generate the three Active Record encryption values:

     ```bash
     # in a meilisearch/lab checkout
     cd saas && bin/rails db:encryption:init
     ```

     Put `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY`,
     `ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY` and
     `ACTIVE_RECORD_ENCRYPTION_KEY_DERIVATION_SALT` in
     `/etc/scrapix/scrapix.env` **before** the deploy, and back them up: without
     them the stored Meilisearch keys cannot be read again.
   - Set `LAB_EVENTS_SECRET` and `LAB_SERVICE_TOKEN` on Rails (section A) and
     check `SCRAPIX_ENGINE_URL` (section C.2). Leave `LAB_CRON_ENABLED` unset
     until step 6 is done.
   - Set `RAILS_MAX_THREADS` to at least `5` on Rails (the Puma default is
     3; the database pool follows it). Every credential the engine has not
     cached is now a Rails request (`/internal/auth/introspect`), and the
     engine runs up to 32 of them at once.
   - Deploy Rails and run its migrations (section B first). A data migration
     encrypts the existing Meilisearch engine keys. The release only adds things
     (the internal endpoints, encryption), so nothing else changes for users.
   - Check the internal API answers with the service token:

     ```bash
     curl -s -H "Authorization: Bearer $LAB_SERVICE_TOKEN" \
       http://127.0.0.1:8091/internal/ping   # {"ok":true}
     ```
   - Check that SolidQueue runs the recurring jobs (`process_lab_events` every
     10 s, `run_due_crawl_configs` every 30 s, `cleanup_oauth_tokens` hourly;
     section C.4), and that an unsigned event batch is refused with `401`, not
     `503` (`503` means `LAB_EVENTS_SECRET` is not set on Rails; section C.5):

     ```bash
     curl -s -o /dev/null -w '%{http_code}\n' -X POST \
       -H 'Content-Type: application/json' -d '{"events":[]}' \
       http://127.0.0.1:8091/internal/events   # expect 401
     ```
3. **Create the engine database and its role** on the existing PostgreSQL:

   ```sql
   CREATE ROLE scrapix_engine LOGIN PASSWORD '<generated>';
   CREATE DATABASE scrapix_engine OWNER scrapix_engine;
   ```
4. **Give the engine its own environment, start it once so it migrates, then
   stop it.** On qdq-server the engine and Rails share
   `/etc/scrapix/scrapix.env`, which holds Rails' `DATABASE_URL` and
   `JWT_SECRET`. Do **not** edit those lines: scope the change to the engine's
   unit with a second `EnvironmentFile` (later files win, and this one only
   affects `scrapix-api`):

   ```ini
   # /etc/systemd/system/scrapix-api.service.d/lab-split.conf
   [Service]
   EnvironmentFile=/etc/scrapix/scrapix-engine.env
   ```

   ```bash
   # /etc/scrapix/scrapix-engine.env (mode 600)
   DATABASE_URL=postgres://scrapix_engine:<password>@127.0.0.1:5432/scrapix_engine
   LAB_URL=http://127.0.0.1:8091
   ```

   Run `systemctl daemon-reload`. The engine still reads `LAB_EVENTS_SECRET` and
   `LAB_SERVICE_TOKEN` from the shared file, ignores its `JWT_SECRET`, and
   ignores a leftover `LAB_EVENTS_URL` once `LAB_URL` is set, so nothing needs
   removing from it. With the public route still out of Caddy (step 1), start
   the new binary; once the log shows it is serving, stop it. The data-move
   script refuses to run against tables that do not exist yet.
5. **Move the data.** One time, with the engine stopped:

   ```bash
   deploy/lab-split/move-engine-data.sh \
     "postgres://<admin>@127.0.0.1:5432/scrapix" \
     "postgres://scrapix_engine:<password>@127.0.0.1:5432/scrapix_engine"
   ```

   It copies `jobs`, `job_results` and `lab_events` (so undelivered charges move
   with the data), compares row counts, and refuses to run twice. The Lab's
   copies are left in place: they are the rollback path and are dropped only by
   the cleanup release.

   If it refuses with `engine table … already has N rows` (the step 4 start
   served traffic after all), look at what is there first: an undelivered row
   in the engine's `lab_events` is a real charge. Let the engine deliver it
   (start it with the public route still out, wait until
   `SELECT count(*) FROM lab_events WHERE delivered_at IS NULL` is 0 on
   `scrapix_engine`, stop it), then empty the engine tables and run the
   script again:

   ```sql
   -- on scrapix_engine, engine stopped
   TRUNCATE jobs, job_results, lab_events RESTART IDENTITY;
   ```

   Jobs created during that start are lost from the history; nothing else is.
6. **Start the engine** with the drop-in from step 4 in place (`LAB_URL`
   `http://127.0.0.1:8091` and the `scrapix_engine` `DATABASE_URL`; it does not
   use `JWT_SECRET`). If the other services also run the new build, follow the
   service order in "4. Deploy order" below. Put the public API route back in
   Caddy once the checks below pass. Then check:
   - the log shows the Lab ping succeeded (from contract v2 on: the
     `GET /internal/instances/me` boot check; a wrong token or `LAB_URL` stops the
     engine at startup instead);
   - `GET /metrics` shows `scrapix_lab_requests_total{endpoint="ping",outcome="ok"}`
     (`endpoint="instances_me"` from contract v2 on)
     and `scrapix_lab_events_pending` draining to near 0.

   Then set `LAB_CRON_ENABLED=true` on Rails and restart it (section E).
7. **Verify.** Run `verify.sh` (signup, key, billed scrape, a crawl, job
   history) and check analytics through the engine. With a real API key:

   ```bash
   curl -s -H "X-API-Key: $KEY" \
     "http://127.0.0.1:8090/analytics/v0/pipes/kpis.json?hours=24"

   # from a meilisearch/lab checkout (the parity script lives there)
   python3 contracts/analytics_parity.py \
     --rails http://127.0.0.1:8091 --engine http://127.0.0.1:8090 --api-key "$KEY"
   # expect: OK: N paths identical
   ```

   The parity script lists its accepted differences in its header.
8. **Move analytics to the engine.** In Caddy, send the `analytics` path prefix
   to 8090, and drop `analytics` from the console proxy's list of Rails
   prefixes (configured in `meilisearch/lab`). Reload both.
9. **After a clean week,** the cleanup release drops `jobs`, `job_results` and
   `lab_events` from the Lab database and deletes Rails' analytics code. The
   engine's `LAB_EVENTS_URL` fallback stays one release longer.

### Phase 1 rollback

Possible until the cleanup release, because the Lab's tables are still there.
The old engine needs its old environment back, and the new engine must deliver
its pending events before it is stopped: delivery only happens while it runs.

1. **Stop new traffic, but keep the new engine running.** First turn
   `LAB_CRON_ENABLED` off on Rails and restart it, so no scheduled crawl starts
   while you drain. Then take the public API route out of Caddy (or return 503
   there), cancel any running jobs, and wait until nothing is left to deliver
   on `scrapix_engine`:

   ```sql
   SELECT count(*) FROM lab_events WHERE delivered_at IS NULL;  -- must reach 0
   ```

   If it does not fall, Rails is rejecting or unreachable: fix that first
   (`scrapix_lab_events_pending` and the delivered-total metric show it). Only
   then stop `scrapix-api`.
2. **Restore the old environment.** Remove the drop-in
   (`rm /etc/systemd/system/scrapix-api.service.d/lab-split.conf`, then
   `systemctl daemon-reload`) so the unit reads only the shared
   `/etc/scrapix/scrapix.env` again. Check that file still has what the old
   binary refuses to start without: the old `DATABASE_URL` (the Rails
   database), `JWT_SECRET`, and for the engine from the boundary rollout
   `LAB_EVENTS_URL=http://127.0.0.1:8091/internal/events` (the full URL, not the
   base), `LAB_EVENTS_SECRET` and `LAB_SERVICE_TOKEN`. Rails keeps its own
   `JWT_SECRET` throughout; never delete it from the shared file. Leave
   `LAB_CRON_ENABLED` off (step 1) if the old engine runs its own cron
   scheduler, or scheduled crawls fire twice; turn it back on only if it
   does not.
3. **Decrypt the Meilisearch keys, then roll Rails back (required).** The old
   engine reads `meilisearch_engines.api_key` directly and cannot use
   ciphertext. With the encryption secrets still set, run
   (in `meilisearch/lab`) `cd saas && bin/rails db:migrate:down VERSION=20260930000001` (it decrypts
   the keys), then deploy the previous Rails release right away. Rolling Rails
   back is not optional: the phase 1 release still declares
   `encrypts :api_key`, so any engine created or edited on it after the
   `db:migrate:down` is stored encrypted again. It also restores `analytics`
   in the Rails MCP server's route list (the Lab's MCP toolset, in meilisearch/lab),
   so MCP analytics calls go to Rails again, matching the console proxy (next
   step). Check that no key is left
   encrypted (Active Record ciphertext is a JSON object starting with `{"p":`):

   ```sql
   -- on the Lab (Rails) database: must return no rows
   SELECT id FROM meilisearch_engines WHERE api_key LIKE '{"p":%';
   ```

   If it returns rows (an engine was saved between the two), decrypt them
   from the phase 1 release's checkout (now in meilisearch/lab), with the secrets still set:
   (meilisearch/lab) `cd saas && bin/rails runner 'MeilisearchEngine.find_each(&:decrypt)'`
   (what the migration's `down` does; the migration itself has already run).
4. **Start the old binary**, restore the `analytics` route in Caddy and the
   `analytics` prefix in the console proxy (meilisearch/lab), and put the
   public API route back.

Jobs created on the new engine will not appear in the old engine's history. The
Lab's copy of `lab_events` still holds rows the move script copied as
undelivered; the old engine may deliver them again, which is harmless because
the Lab processes each event id once.

## 0. Drain or cancel running jobs first

Upgrade with **no job running**. Wait for running jobs to finish, or cancel
them (`DELETE /job/{id}`), before stopping the old services. A job that spans
the upgrade loses the old frontier's in-memory queue (the new frontier
starts from an empty `FrontierStore`) and has no restored accounting on the
new API, so it can never balance: it ends `FailStalled` after
`JOB_STALL_TIMEOUT_SECS` (30 min) and is **billed** for the pages it
crawled. Pick a window with no scheduled cron runs (or temporarily turn
off `cron_enabled` on the saved configs due in it) so no new job starts
mid-rollout.

## 1. Rails migration and pre-merge checks

Since the Lab split the engine migrates its own database (including the
`jobs.accounting` column), so only the Rails release needs its migrations
(run in `meilisearch/lab`); the order relative to the engine is in
"Lab split phase 1" above.

Before merging to `main`, also run — neither of these ran during
development because Postgres was down locally — the Lab's Rails test suite
(`just test` in a `meilisearch/lab` checkout) and one real accounting
flush/restore round trip against a live Postgres
(create a job, let it accumulate a few events, kill and restart the API,
confirm the job's counters survive and it still reaches a terminal state).

## 2. Create Kafka topics

```bash
rpk topic create scrapix.fetch.feedback --partitions 6
rpk topic list | grep -E 'scrapix\.(jobs\.status|dlq\.urls)'
```

`scrapix.fetch.feedback` carries the crawler's per-URL fetch outcome back to
the frontier (releases the domain politeness slot, feeds robots
`Crawl-delay`/`Retry-After` into the domain's delay) — it must exist before
crawlers that publish to it are rolled out (see "4. Deploy order"). Confirm
`scrapix.jobs.status` and `scrapix.dlq.urls` already exist; create them with
`rpk topic create` if not.

## 3. Environment: `REDIS_URL`, instance ids, wake ports

In `/etc/scrapix/scrapix.env`, set `REDIS_URL` for both `scrapix-frontier` and
`scrapix-crawler`:

```bash
REDIS_URL=redis://<host>:6379
```

This makes frontier admission/dedup state and per-domain politeness state
durable and shared (`FrontierStore`), and lets more than one frontier
instance run if `qdq-server` ever scales it out. Leave `ALLOW_PRIVATE_IPS`
**unset** (it defaults to `false`) — production crawls should keep the SSRF
guard (private/loopback/link-local/unique-local/CGNAT/multicast/unspecified
addresses refused) on.

**Redis persistence.** The frontier queue and seen sets live in that Redis;
the frontier is only as durable as it is. Enable AOF (`appendonly yes`,
`appendfsync everysec`) or at least RDB snapshots on the `REDIS_URL`
instance — without persistence, a Redis restart empties every running job's
queue and those jobs end `FailStalled`. Check with
`redis-cli CONFIG GET appendonly` / `CONFIG GET save`.

**Stable `INSTANCE_ID` / `WORKER_ID`.** Each frontier instance must have a
stable `INSTANCE_ID`, and each crawler and content worker a stable
`WORKER_ID` (e.g. `frontier-1`, `crawler-1`, `content-1`), set per systemd
unit, not in the shared env file. The id names the service's job-control
consumer group (`scrapix.jobs.status`). With the default random id, every
restart joins a *new* group starting at the latest offset: controls
published while the service was down (a Cancel, a Pause) are never seen,
and one abandoned consumer group leaks per restart. The services log a
warning at startup when the id is unset.

**Distinct `WAKE_PORT` per service on one box.** Every worker binary serves
`/metrics` and `/health` on `WAKE_PORT`, default `8081`, which is also the
Lab's Rails port on `hackersearch`. A bind failure only logs a warning, so a
service that loses the race simply has no metrics. Set, per unit:

| Service | `WAKE_PORT` | Prometheus target |
|---------|-------------|-------------------|
| `scrapix-api` | — (serves `/metrics` on `PORT`, 8080) | `localhost:8080` |
| `scrapix-frontier` | `9101` | `localhost:9101` |
| `scrapix-crawler` | `9102` | `localhost:9102` |
| `scrapix-content` | `9103` | `localhost:9103` |

(Unit names as deployed by `qdq-server`; use the next free ports if more
instances run on the box, e.g. a second crawler on `9104`.) Rails keeps
`8081`.

For example, with `systemctl edit scrapix-frontier`:

```ini
[Service]
Environment=INSTANCE_ID=frontier-1
Environment=WAKE_PORT=9101
```

## 4. Deploy order

Deploy in this order — **content workers, then crawlers, then frontier, then
API**:

1. **Content workers** — understand both the old and new message shapes
   (every new Kafka message field is `#[serde(default)]`), so they can absorb
   messages from either old or new crawlers during the rollout window.
2. **Crawlers** — old crawlers publish no `FetchFeedback`, so crawlers must
   go out *before* the frontier starts relying on that feedback to release
   politeness slots. Deploying crawlers before the frontier avoids a window
   where the (already-updated) frontier is waiting on feedback that
   old crawlers never send (it would fall back to the `2 × REQUEST_TIMEOUT`
   safety expiry for every slot in that window, which is correct but slow).
3. **Frontier**.
4. **API** last.

## 6b. Politeness defaults changed (single-site crawls are slower)

The frontier defaults went from `DOMAIN_DELAY_MS=50` /
`CONCURRENT_PER_DOMAIN=50` to `DOMAIN_DELAY_MS=250` /
`CONCURRENT_PER_DOMAIN=4`, and the per-domain slot is now held until the
crawler reports the fetch back. A crawl of a single site is therefore
roughly **5–12× slower** than before (up to ~4 req/s per domain instead of
up to ~20). Multi-domain crawls are much less affected. This is intended
(it stops hammering sites), but tell users who crawl their own site.

To override:

- **Box-wide**, in the frontier's env: e.g. `DOMAIN_DELAY_MS=50` and
  `CONCURRENT_PER_DOMAIN=16` (these are the floor for every job; a job can
  only be made slower than them).
- **Per job**, a job can only *raise* the delay (`rate_limit.per_domain_delay_ms`,
  `rate_limit.requests_per_second`, robots `Crawl-delay`); it cannot go faster
  than the frontier's `DOMAIN_DELAY_MS`.

## 7. Fixed Meilisearch instance on port 7701

As of 2026-09-25, the Meilisearch instance pinned to port 7701 on the

- If it's being retired, repoint whatever job configs or engines still target

## 8. Watch the first jobs

After all services are deployed:

1. Submit a small real crawl and watch it reach `Completed` (not stuck
   `Running`, not `FailStalled`) via `GET /job/{id}/status`.
2. Check that its usage came out right: one `usage.recorded` event with
   `operation: "crawl"` whose `units` (`pages_http`, `pages_browser`) match
   the pages crawled. The Lab prices it with its `pricing.yml`; the engine
   holds no price table.
3. Confirm the completion email was sent (exactly one) and the crawl's
   single `usage_deduction` row landed in the ledger (it is applied by Rails
   a few seconds after the job ends).
4. Cancel a second crawl mid-way and confirm the frontier and workers stop
   dispatching/processing its URLs, and that it's billed for the pages
   crawled before cancellation.

## Known caveats after the rollout

- A frontier **crash** (SIGKILL, OOM, power loss — not a graceful stop)
  between popping a batch from Redis and sending it loses that batch: the
  URLs are counted dispatched but never crawled, and the job ends
  `FailStalled` (billed). A graceful stop (SIGTERM) requeues every unsent
  URL within `DISPATCH_SHUTDOWN_GRACE_MS` (10 s).
- The API's accounting "seen" sets (which drop duplicate outcome events)
  are not persisted. A duplicate outcome whose original was accounted
  before an API restart can be counted twice after it (rare: needs a
  redelivery that straddles the restart).
- Jobs retried from the console ("Retry") resubmit the stored config, in
  which secrets are masked (`***`): Meilisearch API key, webhook auth,
  proxy credentials and custom header values. Re-enter them for a retried
  job that needs them.
